# Day 41 / 60：Trivy 容器安全扫描——把漏洞检查加入发布流程

**日期：2026 年 10 月 30 日。**

Day 38–40 已经能构建并发布镜像，但“镜像构建成功”不代表“镜像安全”。今天在镜像发布前扫描操作系统包和应用依赖中的已知漏洞。

## 1. 今日目标

使用 Trivy 扫描 Docker 镜像，并将扫描作为 CI/CD 的安全门禁：发现达到策略阈值的漏洞时，阻止镜像发布。

## 2. 核心概念

- CVE：公开记录的安全漏洞编号。
- Severity：漏洞严重程度，如 CRITICAL、HIGH、MEDIUM、LOW。
- Fixed version：已提供修复版本的依赖版本。
- SBOM：软件物料清单，描述镜像中包含哪些组件。
- Security gate：发布前必须通过的检查条件。

扫描器报告的是“已知漏洞匹配”，不是系统绝对安全证明。误报、不可利用漏洞、尚无修复版本都需要人工判断和记录。

## 3. 学习材料

- [Trivy Documentation](https://trivy.dev/latest/)
- [Trivy GitHub Action](https://github.com/aquasecurity/trivy-action)
- [GitHub Actions Security](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)

## 4. Coding Practice

先在本地构建镜像，再扫描：

```bash
trivy image --severity HIGH,CRITICAL your-image:tag
```

查看报告中的漏洞 ID、受影响组件、当前版本、修复版本和严重程度。优先升级有修复版本的直接依赖，重新构建并再次扫描。

将扫描接入 GitHub Actions，顺序应为：

```text
Checkout → Build image → Trivy scan → Pass? → Publish image
```

扫描应发生在 GHCR 发布之前。练习策略：发现 CRITICAL/HIGH 且有修复版本的漏洞时失败；对没有修复版本的漏洞，先记录风险与例外，不要简单地假设忽略就安全。若团队策略要求所有 HIGH 都阻断，则明确采用更严格门槛。

示例命令形式：

```bash
trivy image   --severity CRITICAL,HIGH   --ignore-unfixed   --exit-code 1   your-image:tag
```

这条命令会对存在修复版本的高危/严重漏洞设置失败门槛。生产流水线还应固定 Action 版本或 SHA，并避免 PR 工作流暴露发布凭证。

## 5. 必须完成的实验

1. 扫描当前镜像并保存报告。
2. 找出至少一个漏洞，解释受影响组件与修复版本；若没有发现，记录扫描范围和结果，不要编造漏洞。
3. 升级或替换有问题的依赖/基础镜像。
4. 重建并重新扫描。
5. 在 CI 中证明扫描失败会阻止发布。
6. 对暂时无法修复的漏洞建立例外记录：原因、影响、责任人、复查日期。

## 6. Deliverable

提交 workflow 更新、扫描报告样例（注意不要包含敏感环境信息）和 `SECURITY.md` 或 README 安全说明。

```bash
git add .github SECURITY.md README.md
git commit -m "Day 41: add Trivy container vulnerability scanning"
git push
```

验收：扫描发生在发布前；CRITICAL/HIGH 门槛生效；漏洞有修复或有明确例外记录；密钥未暴露；能解释扫描不等于绝对安全。

**面试题：** 为什么镜像构建成功仍不能直接发布？为什么要关注有修复版本的漏洞？
