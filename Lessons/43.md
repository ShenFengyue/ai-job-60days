# Day 43 / 60：Redis 与缓存——减少重复计算和等待

**日期：2026 年 11 月 1 日。**

AI 应用中，重复的检索、模型调用和会话读取可能增加延迟与成本。缓存可以复用近期结果，但缓存错误也会让用户看到过期或不属于自己的数据。

## 1. 今日目标

理解 Redis、Cache-aside、TTL、缓存键设计与失效策略；为一个适合缓存的只读操作实现缓存，并验证命中率与正确性。

## 2. 核心概念

- Cache：保存近期结果，减少重复工作。
- TTL：缓存条目的过期时间。
- Cache-aside：应用先查缓存，未命中再查数据源并写回缓存。
- Invalidation：数据变化时删除或更新相关缓存。
- Cache stampede：大量请求同时发现缓存过期，齐刷刷打向后端。
- Rate limiting：限制请求速率；与缓存相关但不是同一个概念。

缓存适合重复且允许一定时效性的读取，不适合无条件缓存所有 LLM 输出。

## 4. Coding Practice

选择一个低风险操作，例如公开知识库中固定文档的检索结果，使用 Cache-aside：

```python
async def get_document_summary(document_id: str):
    key = f"doc-summary:v1:{document_id}"
    cached = await redis.get(key)
    if cached is not None:
        return json.loads(cached)

    result = await repository.build_summary(document_id)
    await redis.set(key, json.dumps(result), ex=300)
    return result
```

这是示意代码，按实际 Redis 客户端的同步/异步接口调整。缓存键应包含版本前缀，数据更新时删除或更新键。涉及用户私有数据时，缓存键必须包含可靠的租户/用户隔离维度，并在读取前完成权限检查，不能仅靠用户传来的 ID。

不要把 API Key、完整隐私对话或高敏感数据放进缓存。LLM 结果缓存需要考虑模型版本、prompt 版本、参数、用户权限和上下文；漏掉任一维度都可能返回错误结果。

## 5. 实验与测试

比较缓存关闭与开启时的响应时间、命中率和后端调用次数。测试缓存命中、未命中、TTL 过期、数据更新后的失效、Redis 不可用时的降级，以及不同用户之间绝不串数据。

Redis 不可用时，系统应按业务重要性决定回源、返回降级错误或暂时禁用缓存；不要让缓存故障把整个服务无条件拖垮。
