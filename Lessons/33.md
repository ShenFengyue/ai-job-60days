# Day 33 / 60：LLM Streaming——逐步显示模型回答

**日期：2026 年 10 月 22 日。**

普通请求通常要等模型生成完整回答才返回。Streaming 把生成结果拆成连续片段，让界面提前显示。它改善首 token 体验，但不保证总生成时间缩短。

## 1. 今日目标

为 FastAPI 实现流式接口，理解 HTTP 流、SSE、Python generator 与客户端断开连接。

```text
Browser ← chunk 1 ← FastAPI ← chunk 1 ← LLM
Browser ← chunk 2 ← FastAPI ← chunk 2 ← LLM
Browser ← done   ← FastAPI ← finish ← LLM
```

## 2. 概念

- Chunk：传输片段，不保证等于一个 token 或完整单词。
- Generator：通过 `yield` 逐次产生数据。
- SSE：基于 HTTP 的单向事件流，Content-Type 为 `text/event-stream`。
- Backpressure：消费者速度跟不上生产者时的缓冲与流量控制。
- Disconnect：用户取消或关闭页面后，服务端应尽可能停止上游生成。

SSE 适合服务端向浏览器单向推送；双向实时通信再评估 WebSocket。

## 4. Coding Practice

先创建 `exercises/day33-streaming/main.py`，用假流验证传输：

```python
import asyncio
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

async def fake_stream():
    for part in ["Hello", " ", "streaming", "!"]:
        yield f"data: {part}\\n\\n"
        await asyncio.sleep(0.2)
    yield "data: [DONE]\\n\\n"

@app.get("/stream")
async def stream():
    return StreamingResponse(
        fake_stream(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

运行后用 curl 或浏览器观察片段是否逐步到达。若反向代理缓冲响应，客户端可能看起来仍是一次性收到。

再接入实际模型 SDK 的流式模式。不同供应商的事件字段不同，应转换成自己的统一事件协议，例如：

```json
{"type":"token","text":"Hello"}
{"type":"token","text":" world"}
{"type":"done"}
```

不要把供应商原始事件无条件透传给前端。前端用 Fetch 读取 ReadableStream，使用 `TextDecoder` 的流式模式处理可能跨 chunk 的 UTF-8 字符。

## 5. 异常与边界

测试正常结束、模型错误、空 chunk、用户取消和超时。响应头发出后不能再像普通请求那样随意更改 HTTP 状态码，因此应设计明确的 error event。取消客户端请求时，尽可能取消上游模型生成，避免继续消耗费用。

原生 EventSource 主要用于 GET；如果请求必须携带 POST body，可采用 Fetch streaming，或设计会话式 GET 事件接口。
