# Day 28 / 60：Hybrid Search——让 RAG 同时理解语义与关键词

**日期：2026 年 10 月 17 日。**

今天进入 RAG 检索优化的下一阶段：**混合检索（Hybrid Search）与排序融合（RRF）**。

之前，你已经接触了 RAG、Agent 和评测。现在要解决一个实际问题：用户明明问的是知识库里的内容，为什么系统还是找不到正确的资料？

例如，知识库中有一段文档：

> API 错误代码 E104 表示认证失败。

用户问：“E104 是什么问题？”

纯语义检索可能找到关于身份验证的概述，却漏掉包含 `E104` 的具体文档。纯关键词检索则可能无法很好地处理同义表达。

今天将两种检索方式结合起来，并通过评测判断是否真的变好了。

## 1. 今日学习目标

理解并实现三种检索策略：

| 策略          | 原理             | 优势                             |
| ------------- | ---------------- | -------------------------------- |
| Dense Search  | 向量语义检索     | 能处理同义表达、语义相似的问题   |
| BM25 Search   | 关键词检索       | 擅长匹配专有名词、编号、精确词汇 |
| Hybrid Search | 合并两种检索结果 | 同时利用语义和关键词信息         |

混合检索的关键不是简单地把两种分数相加，而是要合理融合排序结果。今天使用 **Reciprocal Rank Fusion（RRF，倒数排名融合）**，根据文档在不同检索结果中的排名计算综合分数。[Qdrant](https://qdrant.tech/documentation/search-tuning/hybrid-search/)

工作流程：

```
                  用户问题
                     │
              ┌──────┴──────┐
              ▼             ▼
          语义检索         BM25 检索
              │             │
              ▼             ▼
          Top 20 文档     Top 20 文档
              │             │
              └──────┬──────┘
                     ▼
                  RRF 融合
                     │
                     ▼
                  Top 5 文档
                     │
                     ▼
                交给 RAG 生成答案
```

**今天的目标不是追求最复杂的检索架构，而是证明混合检索是否比你现有的检索方式更好。**

## 2. 今天最值得看的 3 份材料

### 材料一：Qdrant 官方混合检索指南

[Hybrid Search in Qdrant](https://qdrant.tech/documentation/search-tuning/hybrid-search/?utm_source=chatgpt.com)

这是今天的核心材料。

重点看三个部分：

- Dense Retrieval 与 Sparse Retrieval 的区别。
- RRF 如何融合两种检索结果。
- 如何用带有相关文档标注的测试集评估检索效果。

这份文档也提醒我们：混合检索会增加索引、存储和查询开销，不能因为它听起来更先进，就默认它一定更好。[Qdrant](https://qdrant.tech/documentation/search-tuning/hybrid-search/)

### 材料二：rank_bm25 官方 GitHub 仓库

[rank_bm25 官方代码与使用说明](https://github.com/dorianbrown/rank_bm25/blob/master/README.md?utm_source=chatgpt.com)

为什么选它？

因为它允许你直接在 Python 项目里实现 BM25，不需要为了学习关键词检索就先部署一个完整的搜索服务器。

今天主要理解三个操作：

1. 把文档切分成词语。
2. 建立 BM25 索引。
3. 输入问题，返回相关文档排名。

官方示例使用 `BM25Okapi` 建立索引，通过 `get_scores()` 计算相关性分数。[GitHub](https://github.com/dorianbrown/rank_bm25/blob/master/README.md?utm_source=chatgpt.com)

### 材料三：Qdrant 官方检索相关性评测指南

[Measuring Retrieval Relevance](https://qdrant.tech/documentation/search-evaluation/retrieval-relevance/)

重点理解两个指标：

- **Recall@K**：前 K 个结果找到了多少相关文档。
- **MRR**：第一个相关文档排得有多靠前。

对 RAG 而言，Recall@K 尤其重要，因为相关资料完全没有进入候选结果时，后面的 LLM 就无法直接利用它。[Qdrant](https://qdrant.tech/documentation/search-evaluation/retrieval-relevance/)

**建议学习顺序：先理解混合检索，再看 BM25 的代码，最后学习如何评测。总共围绕一个项目，不再额外堆课程。**

### 第一步：安装依赖


这里使用 `jieba` 进行中文分词。如果你的知识库只有英文，可以换成更简单的英文分词方法。

### 第二步：创建 `retrieval/hybrid.py`

下面的代码实现 BM25 检索和 RRF 排名融合。

```
import jieba
from rank_bm25 import BM25Okapi


def tokenize(text: str) -> list[str]:
    return [
        word.strip().lower()
        for word in jieba.cut(text)
        if word.strip()
    ]


def build_bm25(chunks: list[dict]):
    tokenized_chunks = [
        tokenize(chunk["text"])
        for chunk in chunks
    ]
    return BM25Okapi(tokenized_chunks)


def bm25_search(
    query: str,
    chunks: list[dict],
    index,
    top_k: int = 20,
) -> list[str]:
    scores = index.get_scores(tokenize(query))

    ranked_indices = sorted(
        range(len(chunks)),
        key=lambda i: float(scores[i]),
        reverse=True,
    )

    return [
        chunks[i]["id"]
        for i in ranked_indices[:top_k]
        if scores[i] > 0
    ]


def reciprocal_rank_fusion(
    rankings: list[list[str]],
    k: int = 60,
    top_k: int = 5,
) -> list[str]:
    scores = {}

    for ranking in rankings:
        seen = set()

        for rank, doc_id in enumerate(ranking, start=1):
            if doc_id in seen:
                continue

            seen.add(doc_id)

            scores[doc_id] = (
                scores.get(doc_id, 0)
                + 1 / (k + rank)
            )

    return sorted(
        scores,
        key=scores.get,
        reverse=True,
    )[:top_k]
```

这里假设你的文档切片采用如下结构：

```
chunks = [
    {
        "id": "doc_01",
        "text": "API error E104 indicates authentication failure."
    },
    {
        "id": "doc_02",
        "text": "Authentication verifies the identity of a user."
    }
]
```

如果你现有项目使用 `chunk_id` 而不是 `id`，或者用其他字段保存文本，只需要适配字段名。

### 第三步：接入现有语义检索

你已有的语义检索函数叫什么并不重要，关键是让它返回文档 ID 排名。

例如，假设原来的语义检索返回：

```
dense_ids = [
    "doc_02",
    "doc_05",
    "doc_01",
]
```

BM25 返回：

```
sparse_ids = [
    "doc_01",
    "doc_08",
    "doc_02",
]
```

就可以执行：

```
hybrid_ids = reciprocal_rank_fusion(
    rankings=[dense_ids, sparse_ids],
    k=60,
    top_k=5,
)
```

然后根据返回的 ID 找到对应的文本切片，交给原有 RAG 生成逻辑。

**注意：这段代码是检索融合模块，不是完整的 RAG 程序。** 你需要调用现有的语义检索函数，并将两种检索结果传入它。不要因为示例里的函数名不同而重写原有项目。

### 第四步：建立检索评测集

新增 `evaluation/retrieval_cases.json`。

至少准备 10 个问题，每个问题都要标记预期相关的文档 ID。

示例：

```
[
  {
    "query": "E104 是什么错误？",
    "relevant_doc_ids": ["doc_01"]
  },
  {
    "query": "用户身份是如何验证的？",
    "relevant_doc_ids": ["doc_02"]
  }
]
```

实际项目中，需要使用你知识库里真实存在的文档 ID，并补足至少 10 个案例。

尽量覆盖三类问题：

- 精确关键词：错误代码、产品型号、专有名词。
- 语义问题：用户没有使用文档里的原词。
- 混合问题：既包含专有名词，又需要理解问题含义。

相关文档的标注必须来自实际知识库，不能为了让指标好看而随意指定。

### 第五步：比较三种检索方式

使用相同的评测集、相同的文档库和相同的候选数量，分别运行：

1. Dense Search。
2. BM25 Search。
3. Hybrid Search。

至少比较 `Recall@5`，并记录 `MRR@5`。

其中，`Recall@5` 可以这样计算：

\[ Recall@5 = \frac{\text{前5个结果中的相关文档数}} {\text{所有已标注的相关文档数}} \]

假设某个问题有两篇相关文档，前五名只找到了其中一篇，那么这个问题的 `Recall@5` 就是 0.5。

**今天不要求混合检索一定获胜。** 如果它的指标没有改善，就记录实际结果，并分析是 BM25 没有找到新文档，还是 RRF 没有把正确文档排到前面。

### 两道面试题

**Q1：为什么 RAG 有时需要 Hybrid Search，而不是只使用向量检索？**

答题思路：向量检索擅长语义相似度，但可能遗漏精确标识符和特定词语；BM25 擅长关键词匹配，但不一定能理解同义表达。混合检索结合两者的优势，再通过排序融合生成统一结果。是否值得采用，需要在真实评测集上验证。

**Q2：为什么不能直接把向量分数和 BM25 分数相加？**

答题思路：两种检索的分数尺度可能不同，直接相加可能让其中一种检索主导结果。RRF 通过排名而不是直接比较原始分数来融合结果。它是一个实用的起点，但最终仍需根据数据评测。
