# Day 60 / 60：Employment Readiness Gate——结束无期限准备，进入真实市场

**日期：2026 年 11 月 18 日。**

今天不是课程结束庆祝，而是一次诚实的能力验收。目标是判断你是否具备进入 AI 应用工程岗位面试与实际开发的基础。未通过的项目要如实记录，但不意味着必须从 Day 1 重来。

## 1. 最终验收门槛

### 产品交付
- [ ] 3 个 AI 项目有清晰用途、README、架构说明和真实功能。
- [ ] 至少 2 个 Demo 可访问，或有可复现的本地启动说明。
- [ ] 核心路径有测试与评估证据。
- [ ] 已知限制和失败模式写清楚。

### 工程能力
- [ ] 能独立创建 Python 环境、安装依赖、调用 API、处理异常。
- [ ] 能使用 Git 完成修改、commit、push 和基本分支协作。
- [ ] 能构建 FastAPI 服务并进行输入校验、测试和配置管理。
- [ ] 能解释数据库、Docker、CI/CD、日志、指标和基本安全。
- [ ] 能定位 API、部署、检索或工具调用中的常见故障。

### AI 应用能力
- [ ] 能从原理解释 Embedding、RAG、检索、reranking、引用。
- [ ] 能解释 tool calling、Agent loop、state、memory 与失败恢复。
- [ ] 有固定测试集，能比较系统质量，而非只凭主观感觉。
- [ ] 能说明模型调用的延迟、token 与成本约束。

### 求职能力
- [ ] 有针对目标岗位的简历与作品集。
- [ ] 能在 90 秒、5 分钟和 15 分钟讲清项目。
- [ ] 完成至少一次技术面试模拟。
- [ ] 有真实投递记录和持续跟进机制。

## 2. 不要把清单当成伪造通过

每项标记：
- PASS：有代码、测试、Demo 或真实面试表现作为证据。
- PARTIAL：做过但不稳定，或缺少验证。
- NOT YET：尚未完成。

不要因为仓库里存在一个文件就打勾。文件存在不等于功能实现；测试通过也不等于生产可靠。

## 3. 最终自测

在不看教程的情况下：
1. 用 Python 调用一次模型 API，处理超时和错误。
2. 解释并画出 RAG 请求链路。
3. 解释一个 Agent 如何调用工具并处理失败。
4. 启动一个容器化 API。
5. 制造一次错误并从日志定位。
6. 用项目证据讲清一个重要技术取舍。

做不到时记录具体缺口，安排短周期补齐，不要重新开始整套 60 天课程。

## 4. 下一阶段计划

未来 30 天并行推进：
- 求职：每周定向投递、跟进、面试复盘。
- 工程：只修复影响交付和面试的高优先级缺口。
- 产品：持续迭代一个最有用户价值的项目，获取真实用户反馈。

继续学习的依据应来自真实岗位要求、用户问题和系统故障，而不是为了完成课程数量。

## 5. Deliverable

创建 `job-search/day60-readiness.md`，包含每项 PASS/PARTIAL/NOT YET、证据链接、最大三个缺口和未来 30 天计划。

```bash
git add job-search/day60-readiness.md
git commit -m "Day 60: complete AI engineering readiness review"
git push
```

## 6. 最终判断

课程的目的不是让你“学完 AI”，而是让你拥有持续交付的工程闭环：

```text
理解需求 → 设计系统 → 编写代码 → 测试评估
    → 部署运行 → 观察故障 → 修复迭代 → 交付价值
```

如果你已经能在 3–7 天内独立构建一个范围清晰的小型 AI 应用，并能解释其可靠性、成本和边界，就应该把更多时间投入真实产品与真实面试，而不是无限期准备。

**Day 60 的成功标准：从学习者转向持续交付者。**
