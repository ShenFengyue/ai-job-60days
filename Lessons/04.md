## Day 4｜LLM 请求与响应：理解模型到底收到了什么、返回了什么

今天对应 **Day 4**。从 2026 年 9 月 5 日算 Day 1，2026 年 9 月 8 日就是 Day 4。

今天不要急着学“高级 Prompt”。先把一次 LLM 调用拆开看清楚：**消息结构、system/user/assistant 角色、token、上下文窗口、temperature、model，以及 API 返回结果的结构**。后面做 CLI Chat、RAG 和 Agent 时，这些都是基础。

### 1）今日学习目标

完成今天后，你应该能：

- 解释 `system`、`user`、`assistant` 三种消息的作用；
- 看懂一份聊天请求的 JSON；
- 解释“上下文”为什么会影响模型回答、成本和长度；
- 区分 `model`、`temperature`、`max_tokens` 这类参数；
- 从 API 返回的 JSON 中正确提取文本、用量和结束原因；
- 用同一个程序切换不同 system prompt，观察行为变化。

### 2）最值得看的 4 个材料

**材料 1：Hugging Face Agents Course｜Messages and Special Tokens**
这是今天最适合你的主材料。它把对话消息如何被组织、为什么角色很重要、聊天模板如何把消息转换为模型可处理的输入讲得很清楚，而且是实践导向，不会一上来陷入模型训练细节。[Hugging Face](https://huggingface.co/learn/agents-course/en/unit1/messages-and-special-tokens?utm_source=chatgpt.com)

**材料 2：Hugging Face Transformers｜Chat Templates**
重点看 `apply_chat_template()`、`role`、`content`、`add_generation_prompt`。即使你今天主要通过 API 调模型，也应该知道 API 背后本质上仍然是在组织一组消息；不同模型的聊天模板可能不同。[Hugging Face](https://huggingface.tw/docs/transformers//chat_templating?utm_source=chatgpt.com)

**材料 3：OpenAI 官方 API 文档**
重点只看请求体和响应体：消息数组、模型选择、输出文本、usage、finish reason。今天不是为了换供应商，而是建立一份通用的“LLM 请求/响应解剖图”。[Tom's Guide](https://www.tomsguide.com/ai/claude/claude-fable-5-1-is-here-this-one-prompt-shows-what-it-can-really-do?utm_source=chatgpt.com)

**材料 4：你当前使用的模型供应商官方 API 文档**
把 Day 2 的程序重新打开，逐字段核对：`model`、`messages`、`stream`、返回 JSON。今天要形成的能力不是背某一家 API，而是能够自己阅读 API 文档并定位字段。

### 3）必须完成的 coding practice

在本地创建：

```
exercises/day04-llm-cli/
├── main.py
├── README.md
└── requirements.txt
```

把 Day 2 的单次调用改成一个最小 CLI 对话程序：

```
import os
import requests
from dotenv import load_dotenv

load_dotenv()

api_key = os.getenv("DEEPSEEK_API_KEY")
url = "https://api.deepseek.com/chat/completions"

messages = [
    {
        "role": "system",
        "content": "你是一个严谨、简洁的 Python 教师。"
    }
]

while True:
    user_input = input("你：").strip()

    if user_input.lower() in {"exit", "quit"}:
        print("对话结束。")
        break

    messages.append({
        "role": "user",
        "content": user_input
    })

    payload = {
        "model": "你的可用模型名",
        "messages": messages,
        "temperature": 0.2,
        "stream": False,
    }

    response = requests.post(
        url,
        headers={
            "Authorization": f"Bearer {api_key}",
            "Content-Type": "application/json",
        },
        json=payload,
        timeout=30,
    )
    response.raise_for_status()

    data = response.json()
    assistant_text = data["choices"][0]["message"]["content"]

    print(f"AI：{assistant_text}\n")

    messages.append({
        "role": "assistant",
        "content": assistant_text
    })
```

你要完成 3 个实验：

1. **删除历史消息实验**：每次只发送当前问题，和保留完整 `messages` 的版本比较。观察模型是否还能理解“刚才”“上一个问题”等指代。
2. **system prompt 实验**：把 system prompt 分别改成“简洁教师”“严格代码审查员”“鼓励型教练”，用同一个问题测试三次。
3. **temperature 实验**：用同一个问题分别测试低值和高值，记录回答的稳定性、发散程度和格式变化。

把每次实验结果保存成：

```
exercises/day04-llm-cli/results.json
```

建议结构：

```
[
  {
    "experiment": "system_prompt",
    "setting": "strict_code_reviewer",
    "input": "什么是 Python 函数？",
    "output": "..."
  }
]
```

### 5）今天的验收标准

你必须能够不看资料回答：

1. 为什么 `system` 不是普通的用户问题？
2. `assistant` 历史消息为什么要放回下一次请求？
3. 什么叫上下文？
4. 上下文越长，为什么通常会带来成本、延迟或长度限制问题？
5. temperature 改变的主要是什么？
6. 模型名为什么不能随便写？
7. 为什么同一个问题，在不同 system prompt 下会得到不同回答？
8. 如果不保存历史消息，为什么“继续刚才的话题”容易失败？

最终通过标准：

> 你可以在终端启动程序，连续对话至少 5 轮；程序能保留历史消息；你能用实验结果解释 system prompt 和 temperature 对输出的影响。
