## Day 13｜Reranking：让“召回结果”变成“更值得交给模型的结果”

今天是 **Day 13（2026 年 9 月 17 日）**。昨天你完成了 RAG 的第一轮评估，已经能回答：

- 检索到了什么；
- 回答是否有依据；
- 哪个版本更好。

今天进入一个非常关键、也很适合面试讲解的检索优化技术：

> **先用 embedding 快速召回一批候选，再用 Cross-Encoder / Reranker 逐条重排，最后把更相关的少量 chunks 交给 LLM。**

完整链路变成：

```
用户问题
→ Dense Retriever 召回 top-N
→ Cross-Encoder 对 query-document 逐对打分
→ 重新排序
→ 取 top-k
→ 送入 RAG
```

Sentence Transformers 官方文档明确说明：Cross-Encoder 通常比 bi-encoder 有更高的相关性判断能力，但需要对每个 query-document 对单独计算，因此速度更慢；常见做法正是对第一阶段召回的 top-k 结果进行二次排序。[GitHub](https://github.com/huggingface/sentence-transformers/blob/main/docs/cross_encoder/usage/usage.rst?utm_source=chatgpt.com)

------

## 1）今日学习目标

今天完成后，你应该能：

- 解释 embedding retriever 和 reranker 的分工；
- 区分 bi-encoder 与 Cross-Encoder；
- 用一个官方或 Hugging Face 上的 Cross-Encoder 模型重排候选 chunks；
- 比较 rerank 前后的 top-k 结果；
- 计算一个简单的 Recall@k / MRR@k；
- 理解为什么 reranker 不应该直接扫描全部文档；
- 找出 reranker 的速度—质量权衡。

今天只记住这个工程原则：

```
Retriever 负责“快速扩大召回”
Reranker 负责“更准确地排序”
LLM 负责“基于最终上下文生成答案”
```

### 第一步：保留 Day 11 的 dense retrieval

先用 embedding + FAISS 召回 **top_n=5**，不要直接只取 top-1。

```
def dense_retrieve(query, model, index, chunks, top_n=5):
    query_embedding = model.encode(
        [query],
        convert_to_numpy=True,
        normalize_embeddings=True,
    ).astype("float32")

    scores, indices = index.search(query_embedding, top_n)

    results = []
    for score, idx in zip(scores[0], indices[0]):
        item = chunks[int(idx)].copy()
        item["dense_score"] = float(score)
        results.append(item)

    return results
```

你今天要明确观察：

> 第一阶段的目标不是马上找出最终答案，而是尽量别漏掉真正相关的候选。

### 第三步：实现 rerank

```
def rerank(query: str, candidates: list[dict], reranker, top_k: int = 3):
    pairs = [
        (query, candidate["text"])
        for candidate in candidates
    ]

    scores = reranker.predict(pairs)

    reranked = []
    for candidate, score in zip(candidates, scores):
        item = candidate.copy()
        item["rerank_score"] = float(score)
        reranked.append(item)

    reranked.sort(
        key=lambda item: item["rerank_score"],
        reverse=True,
    )

    return reranked[:top_k]
```

这里要注意：

- dense score 和 rerank score 不是同一种分数；
- 不要把两个分数直接相加；
- 先分别观察排序，再决定是否需要复杂融合。

### 第四步：比较 rerank 前后排序

对至少 4 个 query 保存：

- dense top-5；
- reranked top-3；
- 最终送给 LLM 的 top-3。

建议结果结构：

```
[
  {
    "query": "What practical steps are recommended?",
    "dense_results": [
      {
        "chunk_id": "fixed-1",
        "dense_score": 0.8123,
        "text": "..."
      }
    ],
    "reranked_results": [
      {
        "chunk_id": "fixed-3",
        "dense_score": 0.7741,
        "rerank_score": 8.1432,
        "text": "..."
      }
    ]
  }
]
```

至少找出一个：

- reranker 改善排序的案例；
- reranker 没有改善、甚至变差的案例。

不要默认 reranker 一定更好。它的效果取决于：

- 模型与语言匹配；
- 文档领域；
- 候选数量；
- query 是否清晰；
- chunk 是否切得合理。

### 第五步：加入简单指标

使用你 Day 12 的评估集，为每个问题准备一个或多个“正确 chunk ID”。

例如：

```
{
  "id": "q1",
  "question": "What is the main purpose of this document?",
  "relevant_chunk_ids": ["paragraph-0", "fixed-1"]
}
```

实现：

```
def recall_at_k(results: list[dict], relevant_ids: set[str], k: int) -> float:
    returned_ids = {
        item["chunk_id"]
        for item in results[:k]
    }
    return 1.0 if returned_ids & relevant_ids else 0.0
```

再实现一个简单的 MRR：

```
def reciprocal_rank(results: list[dict], relevant_ids: set[str]) -> float:
    for rank, item in enumerate(results, start=1):
        if item["chunk_id"] in relevant_ids:
            return 1.0 / rank
    return 0.0
```

对比：

```
dense top-3
vs
reranked top-3
```

记录：

- Recall@3；
- MRR@3；
- 哪些问题排序发生了变化；
- 哪些问题仍然失败。

### 第六步：做一个速度对比

记录：

- dense retrieval 耗时；
- reranking 耗时；
- 候选数为 3、5、10 时的变化。

不需要做严格 benchmark，但至少写出一个简单结论：

```
候选数量越多，reranker 的计算成本越高；
因此更合理的生产架构是：
先便宜地召回，再昂贵地重排。
```

## 5）今天的验收标准

Day 13 通过，必须满足：

- 能用 FAISS 召回至少 5 个候选 chunks；
- 能使用 Cross-Encoder 对 query-document pairs 打分；
- 能输出 rerank 前后的排序；
- 能保留 dense score 和 rerank score；
- 能对至少 4 个问题做对比；
- 至少计算 Recall@3 或 MRR@3；
- 能记录一次简单的延迟对比；
- 能解释为什么 reranker 通常放在第二阶段；
- 能指出至少一个 reranker 不一定有效的案例；
- 代码、结果、指标和说明已提交到 GitHub。

最终验收问题：

1. bi-encoder 和 Cross-Encoder 的输入结构有什么不同？
2. 为什么 reranker 更准，但通常更慢？
3. 为什么第一阶段不直接用 Cross-Encoder 扫描所有文档？
4. dense score 和 rerank score 能否直接比较？
5. 如果 dense retrieval 没召回正确 chunk，reranker 还能补救吗？
6. 为什么语言与领域匹配会影响 reranker 效果？
7. 什么时候应该减少 top_n，什么时候应该增加 top_n？

最终通过标准：

> 你能把 Day 12 的 RAG 改造成“两阶段检索”，并用指标说明 reranker 是否真的改善了结果，而不是只展示一段更漂亮的输出。

官方 Sentence Transformers 近期已经支持更复杂的 Multi-Vector Encoder 和多模态 reranking，但那是后续路线，不是今天的目标。[GitHub](https://github.com/huggingface/sentence-transformers/releases?utm_source=chatgpt.com)

```
Embedding Retriever
```
