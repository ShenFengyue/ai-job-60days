# Day 22 / 60：LLM 应用的成本、延迟与可靠性优化

**日期：2026 年 10 月 11 日。**

昨天，你给 Agent 加上了可观测性。今天开始利用这些数据优化它。

核心思路：**先测量，再优化，最后用回归测试证明优化没有破坏功能。**

## 1. 今日学习目标

针对现有 `projects/rag-agent`，完成一次小型工程优化：

- **延迟**：一次任务需要等待多久？
- **成本**：每次任务消耗多少 Token、花费多少钱？
- **可靠性**：优化之后，正确率有没有下降？

今天不换框架、不重写项目，只做有数据支持的改进。

## 2. 最值得看的 3 份材料

### ① OpenAI 官方：延迟优化指南

[Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization?utm_source=chatgpt.com)

今天最重要的材料。重点看官方总结的优化方向：减少生成 Token、减少请求次数、并行执行独立任务，以及在不需要 LLM 时避免调用模型。

**为什么选它：** 这些思路不局限于 OpenAI，对其他模型提供商的应用开发也有参考价值。

### ② Langfuse 官方：Token 与成本追踪

[Token & Cost Tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking?utm_source=chatgpt.com)

重点理解如何记录输入、输出 Token，并根据模型定价估算成本。

注意：你使用的模型和 API 提供商可能需要额外配置。没有准确的 Token 使用量和价格信息，就不能声称成本统计准确。

### ③ OpenAI 官方：Prompt Caching

[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching?utm_source=chatgpt.com)

理解为什么重复使用相同的提示词前缀，可能减少处理时间和输入成本。

**注意：** 不同模型提供商的缓存机制和价格不同。今天先理解原理，不要为了使用缓存而重构整个项目。

### 第一步：记录优化前的数据

使用昨天的测试集，运行全部 20 个用例。

记录以下指标：

| 指标              | 含义                           |
| ----------------- | ------------------------------ |
| Task Success Rate | 任务成功率                     |
| Average Latency   | 平均延迟                       |
| P50 Latency       | 一半请求能够在多长时间内完成   |
| P95 Latency       | 95% 的请求能够在多长时间内完成 |
| Average Steps     | 平均执行步骤数                 |
| Token Usage       | 输入与输出 Token 用量          |
| Estimated Cost    | 估算成本                       |

如果暂时拿不到准确 Token 用量或成本，就标记为 `N/A`，不要伪造数据。

### 第二步：选择一个优化点

优先检查 Agent 是否在不必要的地方调用模型。

例如：**简单计算是否也需要先调用一次 LLM 决定使用计算器？**

如果你的系统能够通过明确的规则安全地识别某类简单计算，可以尝试直接调用计算器，跳过不必要的模型请求。

但不要对所有问题硬编码规则。遇到复杂表达式、含糊需求或不确定输入，仍然应当走原有的 Agent 流程。

### 第三步：重新测试

使用完全相同的 20 个测试用例，再运行一次。

比较优化前后的指标，尤其检查：

1. 成功率有没有下降？
2. 平均延迟有没有降低？
3. 模型调用次数有没有减少？
4. 有没有出现新的失败案例？

如果没有改善，就撤销优化，并在报告中解释原因。这同样是有效的工程实践。

### 两道面试题

**Q1：如果一个 Agent 延迟很高，你会怎么优化？**

答题思路：先用 Trace 定位耗时步骤，再检查模型调用次数、生成 Token 数量、检索耗时和串行依赖。优先优化测量结果指向的瓶颈，最后用基准测试验证。

**Q2：如果优化后响应更快，但正确率下降了，你会怎么做？**

答题思路：不能只追求速度。比较优化前后的评测结果，定位受影响的用例；如果收益不值得准确率损失，就撤销改动或调整优化策略。
