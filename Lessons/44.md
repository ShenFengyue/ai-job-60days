# Day 44 / 60：Background Jobs——把耗时任务从 API 请求中分离

**日期：2026 年 11 月 2 日。**

Day 42 处理 FastAPI 的应用结构，Day 43 学习 Redis 缓存。今天继续解决另一个生产问题：有些任务不应该占着 HTTP 请求一直等待。比如解析 PDF、批量生成 Embedding、发送邮件、生成长报告、重新索引知识库。

本课的核心不是“把代码丢到后台就算异步”，而是理解任务的生命周期：提交、排队、执行、重试、失败、恢复和追踪。

## 1. 今日目标

## 2. 三种执行方式

| 方式 | 适合场景 | 局限 |
|---|---|---|
| 同步执行 | 快速、必须立即得到结果的操作 | 请求延迟长，容易超时 |
| FastAPI BackgroundTasks | 发送轻量通知、写简单日志等短任务 | 仍在 Web 进程内；进程退出可能丢任务 |
| 独立 Worker + Queue | PDF 解析、Embedding、批处理、长报告等可靠后台工作 | 需要维护队列、Worker 和任务状态 |

**判断原则：** 任务短、失败损失低，可以先用 BackgroundTasks；任务耗时长、必须重试、不能丢失或需要横向扩展，应使用独立任务队列。不要把 BackgroundTasks 当作 Celery/RQ 这类持久化队列的替代品。

## 3. 任务生命周期

```text
Client
  │ POST /tasks
  ▼
API ──写入任务记录──> Database
  │
  └── enqueue(task_id) ──> Queue
                              │
                              ▼
                            Worker
                              │
                   running / success / failed
                              │
                              ▼
                       Database / Logs
  ▲
  │ GET /tasks/{task_id}
Client
```

推荐状态：`queued`、`running`、`succeeded`、`failed`。如果任务支持取消，可以增加 `cancelled`。状态变更必须有明确规则，不能只靠一个布尔值。

任务记录至少包括：task_id、task_type、status、created_at、started_at、finished_at、attempts、error_summary、result_location。不要把大文件或完整敏感内容直接塞进任务记录。

## 4. Coding Practice：先做一个可理解的最小版本

先创建任务函数，模拟耗时的文档处理：

```python
# app/tasks/document_tasks.py
import time

def process_document(document_id: str) -> dict:
    # 这里只模拟解析、切分和索引过程
    time.sleep(2)
    return {
        "document_id": document_id,
        "chunks_created": 3,
        "status": "succeeded",
    }
```

再用 FastAPI BackgroundTasks 观察“响应先返回、任务在后台执行”的基本机制：

```python
from fastapi import BackgroundTasks, FastAPI
from uuid import uuid4

app = FastAPI()
task_status: dict[str, dict] = {}

def run_task(task_id: str, document_id: str):
    task_status[task_id]["status"] = "running"
    try:
        from app.tasks.document_tasks import process_document
        result = process_document(document_id)
        task_status[task_id].update(status="succeeded", result=result)
    except Exception as exc:
        task_status[task_id].update(
            status="failed",
            error=type(exc).__name__,
        )

@app.post("/tasks")
def create_task(document_id: str, background_tasks: BackgroundTasks):
    task_id = str(uuid4())
    task_status[task_id] = {"status": "queued"}
    background_tasks.add_task(run_task, task_id, document_id)
    return {"task_id": task_id, "status": "queued"}

@app.get("/tasks/{task_id}")
def get_task(task_id: str):
    if task_id not in task_status:
        return {"error": "task_not_found"}
    return {"task_id": task_id, **task_status[task_id]}
```

这是**教学用内存版本**，不是生产实现：重启进程后状态会丢失；多 worker 进程之间不共享字典；没有持久化队列、并发控制和自动重试。真实项目必须把任务状态存入数据库，并使用独立 Worker/队列处理重要任务。

## 5. 生产化设计：重试与幂等

任务可能在“外部操作已经成功、Worker 却没来得及写成功状态”时被重复执行。因此至少要考虑：

- **Idempotency：** 同一个任务执行两次，不应产生两份账单、两封邮件或重复数据。
- **Retry：** 只对暂时性错误重试，例如网络抖动、限流；参数错误等永久性错误不应无限重试。
- **Exponential backoff：** 重试间隔逐步增加，并加入随机抖动，避免大量任务同时重试。
- **Max attempts：** 限制最大尝试次数。
- **Dead-letter / failed queue：** 多次失败后保留任务和错误信息，等待人工检查。
- **Timeout：** 为任务设置最长执行时间，避免 Worker 永久卡住。
- **Observability：** 用 task_id 贯穿 API、队列、Worker 和日志。

对于“生成 Embedding 并写入向量库”，可用 document_id + document_version 作为幂等依据；对每个 chunk 使用稳定 ID，重复运行时 upsert，而不是无条件新增。
