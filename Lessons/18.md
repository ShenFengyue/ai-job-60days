# 7）必须做一个 `max_steps` 实验

设置：

```
max_steps=3
```

然后给 Agent 一个明显需要超过 3 步的问题。

观察：

```
Step 1
Step 2
Step 3
STOP
```

然后改成：

```
max_steps=10
```

再运行。

你会看到一个很重要的工程事实：

> **Agent 必须有明确的执行上限。**

否则如果模型一直无法完成任务，系统可能持续调用：

```
LLM
→ Tool
→ LLM
→ Tool
→ LLM
→ Tool
→ ...
```

这不仅浪费时间，也可能产生 API 成本。

# 9）今天必须理解：Memory ≠ Long-term Memory

你可能会在官方文档里看到：

```
memory
```

今天先不要把它理解成：

> “Agent 拥有长期记忆。”

这里的 memory 更接近：

```
当前任务执行过程中的历史状态
```

例如：

```
User question
↓
Step 1
↓
Tool result
↓
Step 2
↓
Tool result
↓
Step 3
```

Agent 必须把前面的信息带到下一步，否则：

```
Step 2
```

根本不知道：

```
Step 1
```

发生了什么。

**长期用户记忆是后面的主题。**

今天不要提前把问题搞复杂。

### 最关键验收题

不用看资料回答：

> **Tool Calling 和 Multi-Step Agent 到底有什么区别？**

合格答案：

> Tool Calling 解决的是“模型如何请求执行某个工具”；Multi-Step Agent 解决的是“模型如何在一个任务中连续进行多次行动，并根据前一步的结果决定下一步”。所以一个 Agent 可以连续进行多个 Tool Calls，而每一次 Tool Call 只是其中的一步。

# 今日面试题

### ① 为什么 Agent 要设计 `max_steps`？

不要回答：

> “防止死循环。”

更完整：

> Agent 的下一步由模型决定，模型可能因为任务理解错误、工具结果异常或提示设计问题持续行动。因此 Runtime 需要限制最大执行步数，防止无限循环，同时控制 latency 和 API 成本。

------

### ② Agent 为什么需要 Observation？

因为：

```
Action
↓
Tool
↓
Observation
```

工具执行后的结果就是下一次 LLM 决策的重要输入。

没有 Observation：

```
Step 1
→ Tool

Step 2
→ LLM 不知道 Tool 做了什么
```

就无法真正形成闭环。
