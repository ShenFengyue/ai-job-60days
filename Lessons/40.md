# Day 40 / 60：GitHub Actions 自动构建与发布 Docker 镜像

**日期：2026 年 10 月 29 日。**

本地容器能运行后，把构建流程放进 GitHub Actions：Pull Request 自动验证镜像能否构建；主分支更新后发布到 GitHub Container Registry（GHCR）。

## 1. 今日目标

理解 CI（自动验证）与 CD（交付发布）的区别，并建立最小镜像流水线。

```text
Pull Request → checkout → build image → 验证（不发布）
main push → checkout → build → 登录 GHCR → push image
```

## 2. 学习材料

- [GitHub: Publishing Docker Images](https://docs.github.com/en/actions/tutorials/publishing-packages/publishing-docker-images)
- [Docker Build Push Action](https://github.com/docker/build-push-action)
- [Docker GitHub Actions](https://docs.docker.com/build/ci/github-actions/)

本课示例按 2026 年 11 月查阅的官方仓库示例采用 actions/checkout v7、docker/login-action v4、docker/setup-buildx-action v4、docker/build-push-action v7。正式项目仍应在实施时复核官方 release，并在安全要求较高时固定到经过验证的完整 commit SHA。[Docker Build Push Action 官方示例](https://github.com/docker/build-push-action)

## 3. Coding Practice

创建 `.github/workflows/publish-image.yml`。把 PR 构建和发布拆成两个 job：PR job 没有写包权限；只有可信的主分支 push job 才有 `packages: write`。

```yaml
name: Build and publish image

on:
  pull_request:
  push:
    branches: [main]

jobs:
  verify:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v7
      - uses: docker/setup-buildx-action@v4
      - name: Build only
        uses: docker/build-push-action@v7
        with:
          context: .
          push: false
          tags: local/ai-app:pr

  publish:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v7
      - uses: docker/setup-buildx-action@v4
      - name: Login to GHCR
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build and push
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

注意：GHCR 镜像名通常要求小写。若仓库 owner/repository 中含大写字母，应先用 metadata action 或 shell 步骤规范化镜像名，再作为 tags 使用。上面的 YAML 展示最小结构，真实仓库要先确认最终镜像名符合 registry 规则。

镜像使用 commit SHA 标签，避免只依赖 `latest`。这样每个镜像都能追溯到源代码版本。

## 4. 验证

1. 创建分支并提交 workflow。
2. 发起 PR，确认 verify job 执行构建但不发布。
3. 合并到主分支，确认 publish job 登录 GHCR 并推送镜像。
4. 检查 tag 与 commit SHA 一致。
5. 拉取镜像并运行健康检查。
6. 查看 Actions 日志，确认没有输出密钥。

## 5. 安全边界

- 使用最小权限；只有 publish job 获得 `packages: write`。
- 不要在 workflow 写个人访问令牌。
- 不要让来自 fork 的 PR 获得发布凭证。
- 定期更新 action；高安全要求可固定完整 commit SHA。
- 不要把 `latest` 当唯一版本标识。

## 6. Deliverable

提交 `.github/workflows/publish-image.yml` 与 README。README 写明触发条件、镜像地址、标签策略、权限和回滚方式。

```bash
git add .github/workflows/publish-image.yml README.md
git commit -m "Day 40: automate Docker image build and publish"
git push
```

验收：PR 触发构建但不发布；主分支 push 能发布镜像；镜像 tag 可追溯；镜像可运行；没有硬编码密钥。
