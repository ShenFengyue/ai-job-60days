# Day 49 / 60：Portfolio Cleanup——把项目整理成别人敢于运行和评估的作品

**日期：2026 年 11 月 7 日。**

项目能在你电脑上运行，不等于它已经是作品集。招聘者需要快速理解项目解决什么问题、如何运行、哪些能力真实可用、质量如何验证。

## 1. 今日目标

对 ResearchAI、Research Agent、XiaoYa 2.0 做一次工程清理：删除死代码、统一配置、补类型提示与测试、修复 README、提供可复现启动方式。

## 2. 清理原则

- Remove before add：先删除无用代码和重复实现。
- Reproducibility：陌生人按文档能从零运行。
- Explicit limitations：诚实说明暂不支持的功能。
- Evidence over claims：用测试、截图、演示和指标证明能力。
- Small surface area：避免为了“看起来高级”引入不必要依赖。

## 3. 检查清单

每个仓库逐项检查：

1. README 首屏说明问题、目标用户、核心功能和演示地址。
2. 安装步骤从全新环境可复现。
3. `.env.example` 只含变量名和占位说明，真实 `.env` 不在 Git 中。
4. 依赖文件准确，无明显未使用依赖。
5. 入口、目录、命名一致。
6. 关键函数有类型提示，复杂模块有必要说明。
7. 单元测试与关键集成测试可运行。
8. 错误处理不吞掉异常，也不泄露内部堆栈给终端用户。
9. 有架构图、主要数据流和技术选择理由。
10. 截图/录屏来自当前真实版本，不用概念图冒充产品。

## 4. Coding Practice

从每个项目选 3 个最重要的用户路径，写一条从输入到结果的验收测试。例如 ResearchAI：上传 PDF → 完成解析 → 提问 → 返回答案与来源。对关键模块运行 lint/type check（如项目已采用 Ruff、mypy 或 Pyright），不要为了工具数量而安装所有工具。

执行：

```bash
pytest -q
```

按项目实际配置运行 lint/type check、构建和启动命令。删除无用代码前先搜索引用并运行测试，避免清理破坏功能。

## 5. README 结构

- 一句话介绍与问题场景
- Demo / Screenshots
- 核心功能
- 架构图
- 技术栈与关键设计决策
- 安装、配置、启动
- 测试与评估
- 安全与隐私说明
- 已知限制与 Roadmap

## 6. Deliverable

三个项目各完成一次清理提交；README、测试结果、架构说明和截图同步更新。不要把没有真正完成的功能写成“已支持”。

```bash
git status
git add .
git commit -m "Day 49: polish AI project portfolio"
git push
```

验收：新环境能按 README 运行；测试通过；密钥未泄露；功能描述与实际一致；每个项目有可查看的证据。

**求职动作：** 把作品集发给一位可信任的人，请对方在 3 分钟内指出最难理解的地方。

每个项目必须记录干净环境的安装命令、Python/依赖版本、测试结果、Demo、架构图、已知限制和个人贡献。请使用 [Job Search Evidence Kit — Day 49](../JOB-SEARCH-EVIDENCE-KIT.md#day-49--portfolio-cleanup-evidence)。项目交付归属见 [Project Delivery Map](../PROJECT-DELIVERY-MAP.md)。
