# Day 45 / 60：AI 应用可观测性——把请求、模型、工具与成本串起来

**日期：2026 年 11 月 3 日。**

Day 35–37 已经建立基础请求日志、Prometheus 指标与告警。今天把观察范围扩展到完整 AI 请求：检索了什么、调用了哪个模型、用了多少 token、工具耗时多久、最终在哪一步失败。

## 1. 今日目标

设计一条可关联的 AI 请求观测链路，记录 request_id、model、latency、token usage、retrieval count、tool name、error type，并区分 logs、metrics、traces。

## 2. 核心概念

- Logs：具体事件与错误详情。
- Metrics：聚合指标与趋势。
- Traces：一次请求跨 API、检索、模型和工具的调用路径。
- Span：Trace 中的一个操作区段。
- Cardinality：指标标签组合数量；高基数会增加监控成本。
- Redaction：在记录前移除密钥和隐私内容。

## 4. Coding Practice

为一次请求设计如下 span：

```text
HTTP request
 ├─ query_rewrite
 ├─ retrieval
 ├─ reranking
 ├─ llm_generation
 └─ tool_execution (0..N)
```

每个 span 记录开始/结束时间、状态、request_id/trace_id 关联信息。模型调用记录供应商、模型名、输入/输出 token 数（若 API 提供）、耗时和错误类型。不要记录完整 prompt、API Key 或原始用户文档。

统一记录结构示例：

```json
{
  "event": "llm_call_completed",
  "request_id": "generated-id",
  "provider": "provider-name",
  "model": "configured-model",
  "duration_ms": 820,
  "input_tokens": 420,
  "output_tokens": 180,
  "status": "success"
}
```

这里的 provider/model/token 数必须来自真实配置或 API usage 返回，不能伪造。若供应商不返回 token usage，应标为 unknown，而不是猜测。

建立低基数指标：请求总量、错误率、模型耗时直方图、token 使用量。模型名称可以作为受控标签；不要把 user_id、request_id、prompt、任意 URL 作为标签。

## 5. 必须完成的排障演练

构造一次失败：检索超时、模型 429、工具参数无效任选其一。使用 trace/request_id 找到整个请求链路，定位具体 span，记录根因、用户影响和修复措施。再制造一次慢请求，比较 P50/P95。

## 6. Deliverable

提交 `notes/observability.md`、日志 schema、测试与 README。文档应包含一次真实或可复现的排障案例。

```bash
git add notes/observability.md
git commit -m "Day 45: document end-to-end AI observability"
git push
```

验收：请求可跨模块关联；模型 token/耗时有来源；指标标签低基数；隐私脱敏；至少完成一次从症状到根因的排障。

**面试题：** 为什么 AI 应用除了 HTTP 延迟，还要监控检索、模型与工具阶段？
