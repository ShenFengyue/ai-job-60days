# Day 37 / 60：Prometheus 告警规则

**日期：2026 年 10 月 26 日。**

指标告诉你服务正在变慢，但如果没人看图表，问题仍可能无人处理。今天将指标转成告警规则，并测试规则是否在正确条件下触发。

## 1. 今日目标

建立两类告警：HTTP 5xx 错误率异常、请求 P95 延迟过高。理解 Prometheus 与 Alertmanager 的分工：Prometheus 计算规则；Alertmanager 分组、去重、路由和通知。

练习阈值只是示例，真实阈值必须依据服务 SLO 和用户影响校准。

## 3. Coding Practice

创建 `monitoring/alerts.yml`。下面假设 Day 36 的指标名和标签确实存在；写规则前先对照 `/metrics`：

```yaml
groups:
  - name: rag-api
    rules:
      - alert: HighServerErrorRate
        expr: |
          sum(rate(rag_requests_total{status_class="5xx"}[5m]))
          / clamp_min(sum(rate(rag_requests_total[5m])), 1) > 0.05
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "RAG API 5xx error rate is high"

      - alert: HighRequestLatencyP95
        expr: |
          histogram_quantile(
            0.95,
            sum by (le) (rate(rag_request_duration_seconds_bucket[5m]))
          ) > 1.5
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "RAG API P95 latency is high"
```

若错误单独记录在 `rag_request_errors_total`，可用它作为分子，但分子分母必须统计同一请求集合。不要直接复制与真实指标不匹配的表达式。

## 4. 验证规则

```bash
promtool check rules monitoring/alerts.yml
```

再写 `monitoring/alerts_test.yml`，模拟正常流量、错误率升高和延迟升高。规则测试要证明触发条件正确，而不只是 YAML 可解析。

- `rate(counter[5m])`：计算时间窗口内计数器平均每秒增长速率。
- `for: 5m`：条件持续满足一段时间后才触发，降低瞬时噪声。
- `histogram_quantile(0.95,...)`：根据 Histogram bucket 估算 P95。

## 5. 告警设计原则

只对用户可感知风险或需要采取行动的情况告警。过多无意义通知会造成告警疲劳。每条规则写明严重程度、影响、排查链接和处理步骤。
