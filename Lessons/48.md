## 1. 今日学习目标

先理解一套完整的评估流程：

```
测试问题 Dataset
       ↓
运行 AI 应用
       ↓
记录检索结果、工具调用、最终回答
       ↓
Evaluation / Graders
       ↓
计算各项指标
       ↓
生成评估报告
       ↓
发现回归问题
```

今天需要自动评估四个方面：

| 评估对象     | 核心问题                   | 主要指标                                       |
| ------------ | -------------------------- | ---------------------------------------------- |
| Retrieval    | 有没有找到正确资料？       | Recall@K、Precision@K                          |
| Citation     | 回答引用的来源是否有效？   | Citation Validity、Coverage                    |
| Agent        | 有没有正确选择和调用工具？ | Tool Call Precision、Recall、F1                |
| Final Answer | 最终回答是否满足要求？     | Required Facts、Forbidden Claims、Faithfulness |

尤其要区分三个概念：

- 检索正确，不代表最终回答正确。
- 回答有引用，不代表引用真的支持回答。
- Agent 调用了工具，不代表它调用了正确的工具。

这也是为什么不能只用一个「回答质量分数」评价整个 AI 应用。

## 2. 今日学习材料

今天只看三个资料，全部是官方技术文档。

**① OpenAI：Evaluate agent workflows**

[OpenAI 官方 Agent 工作流评估指南](https://developers.openai.com/api/docs/guides/agent-evals)

这是今天最值得看的资料。

重点看两个部分：

- Trace grading：通过完整执行记录检查模型调用、工具调用、Guardrails 和 Agent handoff。
- Datasets and eval runs：将测试样本固定下来，重复评估不同版本的系统。

OpenAI 官方推荐先通过 Trace 找到具体问题，再使用 Dataset 和 Eval Runs 做可重复评估。[OpenAI Developers](https://developers.openai.com/api/docs/guides/agent-evals)

特别注意一个近期变化：OpenAI 旧版 Evals 平台已于 2026 年 10 月 31 日进入只读阶段，计划于 11 月 30 日关闭。因此今天不要把旧版 Evals API 当作新项目的基础设施。我们自己构建一个本地评估脚本即可。[OpenAI Developers](https://developers.openai.com/api/docs/guides/evals)

**② Ragas：Evaluation Metrics**

[Ragas 官方评估指标总览](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/?utm_source=chatgpt.com)

重点看三个指标：

- [Faithfulness](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/faithfulness/)：回答中的事实是否能够从检索上下文中得到支持。
- [Context Recall](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/context_recall/)：重要资料有没有被成功检索出来。
- [Tool Call Accuracy](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/agents/)：Agent 是否按照预期调用工具，工具顺序和参数是否正确。

Ragas 的 Faithfulness 会把回答拆成若干事实主张，再检查这些主张是否得到上下文支持；Tool Call Accuracy 则检查工具名称、参数和调用顺序。[Ragas](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/faithfulness/)

今天不要求安装 Ragas。先理解指标，再自己实现一个简单版本。

**③ pytest：Getting Started + Parametrization**

[pytest 官方入门文档](https://www.pytest.org/en/latest/getting-started.html?utm_source=chatgpt.com)

[pytest 参数化测试文档](https://github.com/pytest-dev/pytest/blob/main/doc/en/how-to/parametrize.rst?utm_source=chatgpt.com)

重点理解：

```
def test_answer_contains_source():
    answer = "The paper was published in 2020."
    assert "2020" in answer
```

以及参数化测试：

```
import pytest

@pytest.mark.parametrize(
    "answer, expected",
    [
        ("The answer is 2020", "2020"),
        ("The answer is 2021", "2021"),
        ("The answer is 2022", "2022"),
    ]
)
def test_answer(answer, expected):
    assert expected in answer
```

这样就可以用同一个测试函数检查大量不同的输入。

## 3. Coding Practice：构建自己的 AI Evaluation Harness

今天创建一个独立模块：

```
evaluation/
```

建议结构：

```
evaluation/
├── datasets/
│   └── regression.jsonl
├── adapters/
│   └── app_adapter.py
├── metrics.py
├── run_eval.py
├── tests/
│   └── test_metrics.py
└── reports/
```

今天不需要接入任何新的模型 API，也不需要购买额外服务。

### 第一步：建立测试数据集

创建 `regression.jsonl`。

每条记录代表一个测试案例，例如：

```
{
  "id": "rag-001",
  "type": "rag",
  "query": "这篇论文的主要结论是什么？",
  "expected_chunk_ids": [
    "paper-01-page-2",
    "paper-01-page-3"
  ],
  "expected_citations": [
    "paper-01-page-2"
  ],
  "expected_tool_calls": [],
  "required_facts": [
    "研究对象",
    "主要结论"
  ],
  "forbidden_claims": [
    "未经论文支持的结论"
  ],
  "should_abstain": false
}
```

如果你之前 Day 16 已经创建了 `retrieval_eval.csv`，优先复用它，不要重复造数据。

建议今天先准备 12 条测试案例，后续逐步扩展到 30 条以上。

至少覆盖：

- 正常问题
- 检索不到资料的问题
- 多个资料来源的问题
- 必须引用来源的问题
- 必须调用工具的问题
- 不应该调用工具的问题
- 必须拒绝或回答资料不足的问题

### 第二步：编写评估指标

创建 `metrics.py`。

首先实现 Retrieval：

```
def recall_at_k(relevant_ids, retrieved_ids, k=5):
    relevant = set(relevant_ids)
    retrieved = set(retrieved_ids[:k])

    if not relevant:
        return None

    return len(relevant & retrieved) / len(relevant)
```

这里：

- `relevant_ids`：人工标注的正确资料。
- `retrieved_ids`：系统实际检索出的资料。
- `k=5`：只检查前五条结果。

然后实现 Citation：

检查两个问题：

1. 回答引用的 chunk 是否真的出现在检索结果中？
2. 预期应该引用的资料，是否被实际引用？

再实现 Agent：

比较预期工具调用和实际工具调用：

```
Expected:
search(query="Python")
open_page(url="example.com")

Actual:
search(query="Python")
open_page(url="example.com")
```

计算 Precision、Recall 和 F1。

最后实现 Final Answer：

- 必须出现的事实是否出现？
- 不允许出现的错误说法是否出现？
- 应该回答「资料不足」时，是否真的停止编造？

这里先用确定性的规则检查，不要急着使用 LLM-as-a-Judge。

注意：字符串匹配只能检查明确的规则，不能证明语义正确。真正的 Faithfulness 仍然需要人工审查或经过校准的评估模型。

### 第三步：连接真实 AI 应用

创建 `adapters/app_adapter.py`。

它的职责只有一个：

**把你的 AI 应用接入评估系统，并统一返回结果。**

每个测试案例至少返回：

```
{
  "id": "rag-001",
  "retrieved_chunk_ids": [],
  "citations": [],
  "tool_calls": [],
  "answer": ""
}
```

这里要注意：

不要重新开发一套 RAG 或 Agent。

只需要调用现有项目，把运行结果整理成统一格式。

如果现有项目暂时不能运行，可以先用固定样本测试评估器本身，但这只能算 Harness Smoke Test，不能算真实 AI 应用已经通过回归测试。

### 第四步：实现一键评估

创建 `run_eval.py`。

最终目标是：

```
python evaluation/run_eval.py
```

一次执行完成：

1. 加载测试数据。
2. 运行 AI 应用。
3. 收集检索、引用、工具调用和回答。
4. 计算四类指标。
5. 输出失败案例。
6. 保存 JSON 报告。
7. 如果关键指标不达标，返回非零退出状态。

报告示例：

```
{
  "total_cases": 12,
  "retrieval_recall_at_5": 0.85,
  "citation_validity": 1.0,
  "tool_call_f1": 0.92,
  "answer_rule_pass_rate": 0.83,
  "failed_cases": [
    "rag-004",
    "agent-002"
  ]
}
```

这些只是示意数据，不是你的真实运行结果。

**今天最重要的实验：**

故意修改一个测试案例，让正确引用消失，再运行一次评估。

系统必须发现问题，并指出具体失败的案例。

然后恢复正确结果，再运行一次。

这才是真正的回归测试。

## 5. 今日验收标准

| 项目         | 验收要求                     |
| ------------ | ---------------------------- |
| 测试数据     | 至少 12 个案例               |
| Retrieval    | 能计算 Recall@5、Precision@5 |
| Citation     | 能发现无效引用               |
| Agent        | 能检查工具名称和参数         |
| Final Answer | 能检查必需事实和禁止内容     |
| 自动化       | 一条命令执行完整评估         |
| 报告         | 自动保存 JSON 结果           |
| 回归测试     | 人为制造错误后能够发现       |
| GitHub       | 代码、测试、报告全部提交     |

今天不要求你把所有指标做到 100%。

先让系统具备发现错误的能力，再逐步提高质量。

还有一个重要原则：

**不要只看总体平均分，一定要保留每个失败案例。**

如果 100 个问题里有 95 个表现很好，但有 5 个问题会泄露用户数据，那么平均分再高也不能说明系统安全。

你已经进入实际求职阶段。今天尤其值得关注那些要求 RAG 评估、LLM 质量保障、Agent 可靠性和模型效果优化的岗位。

你不必把自己定位成模型训练研究员。现阶段更有价值的方向是：能调用模型、构建 RAG 和 Agent、部署应用，并且能证明应用质量的人。

**面试题一：如何评估一个 RAG 系统的质量？**

回答时至少覆盖：

- Retrieval Recall@K 和 Precision@K
- Context Recall 和 Context Precision
- Faithfulness
- Citation Validity
- 最终回答的正确性

重点说明这些指标分别测量什么，不能混为一谈。

**面试题二：修改 Prompt 后，如何判断系统有没有退化？**

回答思路：

1. 准备固定测试数据集。
2. 对新旧 Prompt 使用相同测试案例。
3. 收集完整输出和 Trace。
4. 比较检索、引用、工具调用、最终回答。
5. 查看失败案例。
6. 如果关键指标下降，就阻止发布或回滚。

**今天的求职动作：**

找 3 个 AI 应用开发岗位，重点查看是否出现 Evaluation、RAG、Agent、Testing、Observability 等要求。

选择一个最匹配的岗位，完成一次针对性投递，并把今天的 Evaluation Harness 作为作品集证据。

------

今天的核心不是再做出一个能回答问题的 AI。

而是让你能够证明：

**这个 AI 为什么可靠、哪里不可靠、改动之后有没有变好。**

这是从「能做 AI Demo」走向「能交付 AI 产品」非常重要的一步。
