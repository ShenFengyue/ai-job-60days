# Day 36 / 60：Prometheus 指标监控

**日期：2026 年 10 月 25 日。**

昨天解决“某一次请求发生了什么”，今天解决“系统整体运行得怎么样”。日志适合调查事件，指标适合观察趋势、容量与服务质量。

## 1. 今日目标

给 RAG API 增加请求量、错误量和耗时指标，通过 `/metrics` 暴露给 Prometheus 抓取。

## 2. 指标类型

- Counter：只增不减的累计值，如请求总量、错误总量。
- Gauge：可增可减的当前值，如队列长度。
- Histogram：观测值分布，如请求耗时，可估算分位数。

P95 表示 95% 的观测值不超过该值。平均值可能掩盖少数特别慢的请求，因此不能只看平均延迟。

## 3. 学习材料

- [Prometheus Python Client](https://prometheus.github.io/client_python/)
- [Metric Types](https://prometheus.io/docs/concepts/metric_types/)

## 4. Coding Practice

安装 `prometheus-client`，创建 `monitoring/metrics.py`：

```python
from prometheus_client import Counter, Histogram

REQUESTS = Counter(
    "rag_requests_total", "Total HTTP requests",
    ["method", "route", "status_class"]
)
ERRORS = Counter(
    "rag_request_errors_total", "Failed HTTP requests",
    ["route", "status_class"]
)
DURATION = Histogram(
    "rag_request_duration_seconds", "Request duration",
    ["route"]
)
```

在 FastAPI 请求生命周期记录计数和耗时。路由标签应使用模板路径（如 `/documents/{document_id}`），不能使用原始 URL、用户 ID 或 request_id。

参考逻辑：

```python
started = time.perf_counter()
try:
    response = await call_next(request)
    status_class = f"{response.status_code // 100}xx"
    REQUESTS.labels(method, route, status_class).inc()
    if response.status_code >= 500:
        ERRORS.labels(route, status_class).inc()
    return response
finally:
    DURATION.labels(route).observe(time.perf_counter() - started)
```

这是中间件逻辑骨架，需结合项目补齐异常路径与指标暴露方式。避免重复注册导致重复计数。

## 5. 验证

启动 API，调用健康检查 10 次，制造至少 2 次可控失败，再访问 `/metrics` 检查计数与耗时。今天不要求部署 Grafana。

## 6. 常见陷阱

- Histogram 的耗时单位用秒，名称带 `_seconds`。
- 不要使用无限变化的标签，避免高基数。
- 指标不要包含用户内容或密钥。
- 测试全局指标时隔离 registry，避免测试之间互相污染。
