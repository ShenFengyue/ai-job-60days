## Day 12｜RAG 评估：不要再凭“看起来不错”判断系统好不好

今天是 **Day 12（2026 年 9 月 16 日）**。昨天你已经完成了最小 RAG：

```
问题
→ 检索 chunks
→ 拼接上下文
→ LLM 回答
→ 返回来源
```

今天不再增加框架，而是建立真正的工程闭环：

```
RAG 版本 A
→ 固定问题集
→ 记录检索结果与答案
→ 定义评分标准
→ 对比版本 B
→ 找出真正有效的改动
```

今天的核心结论是：

> **没有评估集，你不是在优化 RAG，而是在反复修改后凭感觉挑一个答案。**

### 第三步：先做人工可解释的 baseline 评分

实现下面几个简单函数：

```
def contains_chunk_id(answer: str, chunk_ids: list[str]) -> bool:
    return any(chunk_id in answer for chunk_id in chunk_ids)


def keyword_coverage(answer: str, ground_truth: str) -> float:
    answer_words = set(answer.lower().split())
    truth_words = set(ground_truth.lower().split())

    if not truth_words:
        return 0.0

    return len(answer_words & truth_words) / len(truth_words)


def groundedness_score(answer: str, context: str) -> int:
    """
    0 = 明显引入上下文没有的信息
    1 = 基本基于上下文，但有少量扩展
    2 = 几乎完全能在上下文中找到依据
    """
    print("\n请人工判断 groundedness：")
    print("Answer:", answer)
    print("Context:", context)
    print("输入 0 / 1 / 2：")
    return int(input().strip())
```

你不需要假装这个评分器很科学。今天的目标是：

> 先建立固定标准，再逐步自动化。

### 第四步：定义 4 个核心指标

对每条样本记录：

#### 1. Retrieval Hit

正确答案所需的 chunk 是否出现在 top-k 中：

```
hit = 1 或 0
```

#### 2. Context Precision（简化版）

返回的 chunks 中，有多少与问题真正相关：

```
相关 chunks 数 / 返回 chunks 总数
```

#### 3. Faithfulness（人工版）

答案是否能在检索上下文中找到依据：

```
0 = 无依据
1 = 部分有依据
2 = 基本有依据
```

#### 4. Answer Relevancy（人工版）

答案是否真正回答了问题：

```
0 = 没回答
1 = 部分回答
2 = 直接回答
```

在 `baseline_results.json` 中保存：

```
[
  {
    "id": "q1",
    "question": "...",
    "retrieved_chunk_ids": ["fixed-1", "fixed-3", "fixed-0"],
    "retrieval_hit": 1,
    "context_precision": 0.67,
    "faithfulness": 2,
    "answer_relevancy": 2,
    "answer": "...",
    "notes": "回答有依据，但第二个 chunk 带来少量噪音。"
  }
]
```

### 第五步：做一个明确的改进版本

今天只允许改动一个变量，推荐选择：

- `top_k: 3 → 1`
- 或 `top_k: 3 → 5`
- 或把 system prompt 改成更严格的 grounded answer prompt

例如更严格的 prompt：

```
Answer only with claims supported by the context.
For each claim, cite the chunk ID.
If the context is insufficient, say:
"I don't know based on the provided context."
Do not use outside knowledge.
```

重新运行同一批问题，保存为：

```

```

注意：**问题集、文档、评分规则必须保持不变。**否则你无法知道改进到底来自哪里。

### 第六步：计算总体结果

实现一个汇总函数：

```
def summarize(results: list[dict]) -> dict:
    count = len(results)

    return {
        "retrieval_hit_rate": round(
            sum(item["retrieval_hit"] for item in results) / count, 3
        ),
        "avg_context_precision": round(
            sum(item["context_precision"] for item in results) / count, 3
        ),
        "avg_faithfulness": round(
            sum(item["faithfulness"] for item in results) / count, 3
        ),
        "avg_answer_relevancy": round(
            sum(item["answer_relevancy"] for item in results) / count, 3
        ),
    }
```

## 5）今天的验收标准

Day 12 通过，必须满足：

- 有至少 5 个固定评估问题；
- 至少包含 1 个文档没有答案的问题；
- RAG 保存了检索结果、上下文和最终答案；
- 能计算 retrieval hit rate；
- 能对 context precision、faithfulness、answer relevancy 做评分；
- 完成 baseline 和 improved 两个版本；
- 两个版本只改了一个主要变量；
- 有结果对比表；
- 至少分析 2 个失败案例；
- 代码、数据、结果和 README 已提交到 GitHub。

最终验收问题：

1. 检索命中率高，是否代表答案一定正确？
2. 答案相关性高，是否代表答案一定有依据？
3. `faithfulness` 和 `answer relevancy` 有什么区别？
4. 为什么评估集必须固定？
5. 为什么一次只改一个主要变量？
6. 如果所有问题都答得不错，但检索到的 chunks 很差，说明什么？
7. 如果检索很好但答案经常胡编，应该优先改哪里？

最终通过标准：

> 你能用一组固定问题，量化一个 RAG 版本，并用数据而不是感觉说明另一个版本是否更好。
